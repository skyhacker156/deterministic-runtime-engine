# GUARANTEE_MATRIX.md

**Purpose:** answer, in one place, without requiring a reader to reconstruct
the full audit history:

1. What does Phoenix A actually guarantee?
2. How is each guarantee established?
3. Which guarantees are merely tested rather than enforced?
4. Where does independent verification exist?
5. What is deliberately outside the system?
6. What remains genuinely undecided?
7. Which `CI-` findings have already been closed versus merely documented?

## Reading this matrix correctly

**A–E are epistemic/architectural dispositions, not quality grades.** A row
being graded lower than another is not itself a defect — `GAP-003`'s
deliberate exclusion and `MB-003`'s proven impossibility are both healthy,
honest states for a guarantee to be in. What the grade answers is a single
question: *is this property established, and if so, how would a violation
be caught?*

**Category definitions:**

- **A — Mechanically enforced.** The implementation contains an active
  mechanism that enforces the stated property; a violation would be caught
  automatically, not merely by a human noticing.
- **B — Behaviorally verified.** Tests demonstrate the property holds
  today, but no structural mechanism prevents a future violation from
  slipping in unnoticed.
- **C — Independently anchored.** The property is checked against an
  oracle or evidence source that is not generated by the same mechanism
  being verified — protection against a *shared* fault, not just a
  *divergent* one.
- **D — Known limitation / documentation-only.** The limitation is
  acknowledged in the project's own text but is not implemented as an
  enforced guarantee, and nothing would notice if the documented property
  silently stopped holding.
- **E — Out of scope / unresolved boundary.** Split into three subtypes,
  since collapsing them loses the most important distinction in this
  matrix:
  - **E-P (Proven boundary)** — evidence establishes the property *cannot*
    be demonstrated under the current model. The strongest possible form
    of "not guaranteed," because it's been proven, not merely unattempted.
  - **E-D (Deliberate design exclusion)** — the property could
    theoretically be built, but the architecture intentionally omits it, a
    considered tradeoff.
  - **E-U (Undecided / open)** — not implemented, and no architectural
    decision has closed the question either way.

**Enforcement Basis** (applies to A, B, and C rows — the *how*, distinct
from the grade itself, which is the *whether*):

| Basis | Meaning |
|---|---|
| **Formal** | Mathematical/theorem-level guarantee under explicit, stated assumptions |
| **Runtime** | Production code actively enforces the invariant during normal execution |
| **Structural** | Tests or tooling prevent a prohibited implementation pattern from existing, independent of runtime behavior |
| **Environmental** | Configuration, dependency, or build structure enforces it |
| **Contractual** | An interface/contract mechanism (e.g. an ABC) enforces it |

Two rows can both be grade A while resting on entirely different bases —
`MB-001` (Formal, a theorem) and `GAP-004` (Environmental, a pinned
requirements file) are not the same kind of "enforced," and the table below
keeps that visible rather than flattening it.

## What the matrix says, read as a whole

**Question 3 (merely tested vs. enforced) has a blunt answer: most of
Phoenix A.** B is the largest category by a wide margin. This is not a
criticism on its own — a passing, well-designed test suite is real
evidence — but it means most of this system's guarantees would not
self-detect a future violation; they rely on a human noticing a test
failure caused by an unrelated change, or on the next adversarial campaign
finding it by construction the way `CI-002` was found.

**Question 4 (where does independent verification exist) has a
one-word-shy-of-alarming answer: almost nowhere.** `CI-005` is the only
confirmed C-grade row in the entire matrix, and it earned that grade by
accident — an unrelated test file's independently-pinned expectation
happened to overlap in scope, not because `kernel_state_replay.py` was
designed with an external oracle in mind. The precise architectural
characteristic this reveals, worth stating exactly: **much of Phoenix A
verifies consistency within its own computational lineage — canonical
implementation → record → replay → the same canonical implementation —
which establishes self-consistency, not independent correctness.** A
regression shared across both sides of such a chain is invisible to it by
construction, not by oversight in any one module's design.

**Question 5/6 (deliberately excluded vs. genuinely undecided) were being
conflated before this matrix existed, and shouldn't be.** `MB-003`,
`GAP-001`, `GAP-003`, and `GAP-005` would all have read as "not built" in a
flatter framing. They are not the same kind of absence: `MB-003` is proven
impossible under the current evidence model — the strongest epistemic
status any row in this matrix holds, stronger even than most A grades,
because it forecloses a whole category of future "maybe if we try harder"
proposals. `GAP-003` is a considered tradeoff, revisitable but not an
oversight. `GAP-001` and `GAP-005` are the genuine unknowns — nobody has
decided whether Phoenix A should ever guarantee these, and that's an honest
thing to be able to say in one place.

**Question 7 (which `CI-` findings are closed vs. documented) — all five
are closed, but "closed" means different things.** `CI-002` is the only one
with a code fix; `CI-001`, `CI-003`, `CI-004`, `CI-005` are closed as
*documented* limitations — real, confirmed by construction, correctly
scoped, and deliberately left unfixed because fixing a boundary that's
correctly closed today would mean solving a problem the real system doesn't
have, at the cost of implying a guarantee the architecture was never built
to provide. Closed does not mean "no longer true" — every one of these
findings remains true about the system as it exists today.

**A stopping rule, stated plainly:** this matrix is the first artifact this
session has produced that a reader can consult without reconstructing the
audit history behind it. From here, a new attack needs to justify itself
against a specific row in this table — an unresolved E-U, a B-grade
guarantee whose test coverage looks thin on inspection, a D-grade
canonicality claim not yet checked — rather than "there might be something
else interesting in the repo." That absence of a target is itself the
signal to stop, not a reason to keep searching for one.
